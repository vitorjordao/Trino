# Trino — Agent Guide

Trino is a Rust game engine targeting **Nintendo 64, Nintendo 3DS and PC** from a single
codebase, with a visual editor, console-simulation modes, live reload and emulator-based
testing. This file is the canonical entry point for **any** AI agent (Claude Code, Codex,
Gemini CLI, Cursor, Copilot, …) and a good one for humans.

Roadmap and per-phase acceptance criteria: `PLANO_EXECUCAO_TRINO.md` (Portuguese).
Original architecture rationale: `PLANO_ENGINE_TRINO.md` (Portuguese).
What to build next (ranked): `docs/BACKLOG.md`.

## Working with AI agents (vendor-neutral)

- **Instructions:** this file. `CLAUDE.md` and `GEMINI.md` only import it;
  `.github/copilot-instructions.md` points here. Codex and Cursor read `AGENTS.md` natively.
- **Skills:** canonical in `.agents/skills/<name>/SKILL.md` (the open Agent Skills format,
  read natively by most agents). `.claude/skills/` is a **generated byte-identical mirror**
  for Claude Code — edit only `.agents/skills/`, then `cargo xtask agents sync`
  (`xtask/tests/agents_sync.rs` fails CI on drift and on skills missing from this table).
- **Everything is text and hot-reloads both ways:** scenes, prefabs, materials and fake
  objects are RON files the editor reads and writes; an agent edits the same files and a
  running editor / scene player updates live. Validate with `cargo xtask scene check`,
  art with `cargo xtask model inspect`, and *look* with the editor's screenshot hook.

| Skill | Use it for |
|---|---|
| `add-asset` | sprites, sounds, music, models, fake objects, materials → manifest, bake, verify |
| `blender-asset` | modeling / coloring / rigging / animating a model in Blender for Trino's real limits; export + `model inspect` gate |
| `scene-authoring` | writing scenes, prefabs, materials as text; `scene check`; exporting scenes to console code |
| `editor` | running the editor, screenshot/selection/log hooks for agents, editor code map |
| `build-n64` | ROM build via Docker, N64 pipeline troubleshooting |
| `build-3ds` | .3dsx build via devkitPro, 3DS pipeline troubleshooting |
| `run-emulator` | ares / Azahar runs, emulator test harness, watch loops |
| `test-all` | the CI gates + guard tests, console type-checks, T&L benchmark |
| `engine-feature` | adding/changing an engine service or format end to end: all backends, self-test step, docs, the closing knowledge loop |
| `n64-performance` | per-stage/per-model N64 frame cost (emulated, ares), perf gates, the calibrated cost model, before/after workflow, what worked |
| `ci` | the GitHub Actions jobs, why they're shaped that way, replicating a job locally, debugging red runs |
| `new-project` | `cargo xtask new` (in-repo or `--standalone`), maintaining the templates and `trino-runner-pc` |

**Knowledge loop:** before reporting a task done, write what it taught you into the
skill that owns that kind of work. A trap also gets a line under Pitfalls below. Create a
new skill when none fits. Then run `cargo xtask agents sync`. The steps are in
`engine-feature` › Closing. A skill that turns out wrong gets fixed in the same session.

## Current state

**All 9 roadmap phases (0–8) implemented.** Working today:

- PC 2D rendering (wgpu, console-sim resolutions, golden tests), audio, input.
- Asset pipeline: `assets/manifest.toml` + shared masters + per-platform overrides →
  `cargo xtask assets pc`. Handles = fnv1a(logical path), stable across reloads.
- Live reload: `cargo xtask watch pc` — saving a master rebakes + re-uploads it live;
  saving game source rebuilds the dylib and hot-lib-reloader swaps functions under the
  running state (`apps/pc` feature `reload`).
- **Editor** (`cargo xtask editor`, `crates/editor`): dark themed dockable UI (Inter +
  Phosphor icons) — **Scene view** (real `PcRenderer` at panel resolution, orbit camera,
  z-buffered grid, click picking, move/rotate/scale **gizmo** with snapping, axis widget,
  drag-and-drop from Assets), **Game view** (scene camera at N64/3DS/PC resolution and
  look), Hierarchy tree (parenting by drag, rename, visibility, prefab instances),
  Inspector (components, inline material editing, prefab overrides, scene environment),
  Assets browser (rendered thumbnails), Console, toasts, status bar. Snapshot
  **undo/redo**, copy/paste entities **as RON** (Ctrl+C/V — round-trips through any AI
  chat), keyboard shortcuts (F1). **Play** runs the open scene (`TRINO_SCENE`, live
  reload) or the game, in a separate process. Every UI action writes a text file.
  Agent hooks: the `editor` skill.
- **Content formats** (`trino-scene` crate, versioned RON, hot-reloaded):
  scenes v2 (`scenes/*.scene.ron`: nested entities, 3D transforms in degrees, models +
  materials + animation clip, sprites, tags, prefab instances, environment = camera,
  colored light, fog); **prefabs** (`prefabs/*.prefab.ron`: linked instances,
  per-instance overrides, unpack, nesting with cycle detection — Blender-style);
  **materials** (`assets/materials/*.material.ron`: tint, `Gouraud|Flat|Unlit`,
  emissive, double-sided — all evaluated by the software T&L, so identical on every
  target). v1 scenes migrate on load. `cargo xtask scene check` validates;
  `cargo xtask scene export` turns a scene into `no_std` Rust data
  (`trino_core::SceneNode`) for consoles — `examples/showcase` is the editor's demo
  scene that way (runs on PC with `TRINO_GAME=showcase`, type-checks for N64/3DS), and
  `xtask/tests/showcase_render.rs` proves runtime and exported scenes render
  pixel-identically. ADR: `docs/adr/0004-authored-content.md`.
- **Fake objects**: parametric placeholder models (`*.prim.ron`: box, sphere, cylinder,
  cone, capsule, plane, ramp, torus; size, colors/gradient, pivot, segments) baked to
  TMDL like any glTF — usable on every target immediately; point the manifest `file` at
  the real `.glb` later and every reference stays (same handle). Editor: Create › Fake
  object (Shift+A, live preview), live parameter editing in the Inspector.
- **Rigid animation**: glTF node animations / skins bake into a TMDL skeleton (≤ 32
  joints, each vertex follows one joint — the N64-era limb model) + clips sampled at
  `anim_fps`; `ModelParams::anim` poses a draw; evaluated in `trino_core` on the stack,
  so all three targets animate with no backend code. `cargo xtask model inspect` is the
  art acceptance gate (tris, joints, clips, bounds, N64 budget and calibrated
  N64 cost per draw).
- **N64**: `cargo xtask build n64` produces `target/n64/trino.z64` (Docker
  toolchain image + C shim + Rust staticlib — ABI story in
  `docs/adr/0002-n64-abi-o32-staticlib.md`); `run n64` opens it in ares
  (expected at `ares-v148/` in the repo root, gitignored); `test n64` boots a
  test ROM and asserts on ISViewer magic strings (`TRINO_TEST_PASS/FAIL`), on
  a pixel-exact **emulator golden** (`tests/golden/n64/showcase.png`, from a
  framebuffer dump; `--bless` rewrites it) and on **perf gates**: per-scene,
  per-stage, per-model frame cost in emulated N64 time (`TRINO_PERF_SCENE` /
  `TRINO_PERF_MODEL`), whose T&L work counters must equal the PC baseline and
  whose times must stay under `tests/perf/castle64_n64.toml`. `TRINO_ARES=docker` runs ares from the
  `docker/ares` image (`cargo xtask emulators setup ares`) — what CI does.
  `watch n64` rebuilds + relaunches on save. Skills: `build-n64`, `run-emulator`.
- **N64 look on PC**: the `SimProfile::N64` renderer emulates the console
  output — 3-point filtering + RGBA5551 quantization with the RDP magic-square
  dither (`TRINO_LOOK=off|n64` overrides). Strict mode (`TRINO_STRICT=1` or
  `PcRenderer::set_strict`) panics with an actionable message when content
  busts the profile's `Caps`. The 16-bit write follows the RDP's own rule
  (angrylion `dither.c`), and a **VI dedither pass** runs at `end_frame`
  (`set_vi_dedither`). The N64 shim enables the same dither and VI filter, so
  PC and console match: `xtask/tests/n64_parity.rs` compares the PC frame
  with the ares golden (mean diff about 2.5/255).
- **3DS**: `cargo xtask build 3ds` produces `target/3ds/trino.3dsx` — all
  local (devkitPro install auto-detected; built-in `armv6k-nintendo-3ds`
  Tier 3 target, C shim over libctru + citro2d in
  `crates/platform-3ds/shim/`); `run 3ds` opens it in Azahar (auto-detected
  or `$TRINO_AZAHAR`, or the pinned AppImage from `cargo xtask emulators
  setup azahar`); `test 3ds` asserts the TRINO_TEST_* magic strings by
  tailing Azahar's log (`svcOutputDebugString` channel; the harness seeds or
  patches Azahar's config) and compares a castle64 frame with
  `tests/golden/3ds/castle64_hub.png` within a tolerance. All 3D is drawn
  by citro3d with **per-vertex depth** (`trino_3d_draw`). `build 3ds --selftest` + `test 3ds --no-build`
  split build and boot, as CI does. `watch 3ds`
  rebuilds + relaunches on save. The `SimProfile::N3ds` PC renderer samples
  sprites bilinearly (the 3DS GPU default). Skills: `build-3ds`,
  `run-emulator`.

- **Showcase platformer** (`examples/platformer`, the 2D showcase):
  tilemap + AABB physics from `trino_core::{tilemap,collide}`
  (ASCII levels, zero-alloc parse, substepped collision — deterministic
  across targets, verified by unit tests and the console self-tests), coins,
  goal, camera with bounds, chiptune music loop + SFX. Music flows through
  the whole pipeline (`[music.*]` in the manifest → TSND on PC, wav64
  `--wav-loop` on N64, looped ndsp wavebuf on 3DS). `hello-sprite` stays as
  the minimal example (the hot-reload E2E builds it standalone).
  README media: hero shot via `cargo test -p xtask --test hero_shot --
  --ignored`; gameplay GIF (a bot plays the level on the real renderer) via
  `cargo test -p xtask --test record_gif -- --ignored`.
- **castle64** (`examples/castle64`, the 3D showcase and the default game in
  all three `apps/*`): SM64-style hub + 3 platforming stages + throne room.
  Own 3D AABB physics (axis-resolved with a contact skin — `physics.rs`),
  inertial movement with variable-height jumps, an articulated 5-part purple
  player (torso/arms/legs pivoted at shoulders/hips, real walk cycle),
  patrol boars with stomp kills, lava, moving platforms that carry the
  player, an orbit camera clamped by raycast, tinted doors and a HUD with
  generated digit sprites. The characters and doors are built in Blender by
  `tools/blender/castle64_models.py` (`cargo xtask blender castle64`), with
  only the faces a camera can see. The castle entrance is KayKit's Dungeon
  Remastered doorway (CC0) rebuilt at 75 triangles. The original 1068-triangle
  file stays as the asset pipeline's textured multi-primitive fixture. A
  deterministic waypoint bot (`castle64::bot`) plays the entire game in the
  PC test suite and a full stage inside the ares/Azahar self-tests.
  Generated masters regenerate via `cargo xtask gen-assets`
  (`xtask/src/castle64_assets.rs`); screenshots/GIF via
  `cargo test -p xtask --test c64_shots|c64_gif -- --ignored`.
- **3D (`draw_model`)**: engine-side software T&L (`trino_core::render3d` —
  see `docs/adr/0003-software-tnl-3d.md`): glTF masters bake to the portable
  TMDL format (`[models.*]` in the manifest); the core transforms, lights
  (gouraud, directional + ambient), culls and depth-sorts on the CPU with
  deterministic f32 (own no_std sin/cos/sqrt); backends only rasterize
  screen-space colored triangles (`rdpq_triangle` shade / a citro3d vertex
  buffer / a wgpu vertex-color pipeline interleaved with sprites). `set_camera` +
  `set_light` (colored directional + ambient + distance fog) + `draw_model` /
  `draw_model_matrix` (hierarchies) on all three targets — `ModelParams` is the
  per-draw surface: tint (locked doors, glow pulses — no separate baked meshes),
  emissive, `Shading::{Gouraud, Flat, Unlit}`, double-sided, animation pose.
  Meshes outside the frustum are culled whole from a baked bounding sphere; a
  per-draw vertex cache transforms/lights shared vertices once (CPU cost is
  tracked by `xtask/tests/bench_tnl.rs`). Strict mode enforces
  `max_tris_per_frame`. The platformer shows a spinning cube.
  Triangles are clipped against the near plane + a 1.5x guard-band frustum
  (bounded coordinates — RDP fixed-point safe); edges spanning > 3 units of
  view depth are bisected; `math3d` ships deterministic `sin/cos/sqrt/atan2`.
  Occlusion is **z-buffered** on every target (per-vertex normalized depth
  in `ScreenTri::z`: wgpu depth buffer on PC, RDP hardware z-buffer on N64,
  per-vertex depth through citro3d on 3DS) — interpenetrating geometry
  resolves per pixel; the `occlusion` self-test step proves it on every target. Consecutive `draw_model` calls still form a depth-sorted batch
  (tie-break + blending order; flushed on sprite draws, camera changes and
  `end_frame`). **Textured 3D**: one texture per draw (TMDL `TXUV`/`TXID`,
  `ModelParams.texture`, material `texture`), on all three targets.

- **Scaffolding + release**: `cargo xtask new <name>` renders
  `templates/new-game/` into `examples/<name>` (game crate + its own
  AGENTS.md; the workspace glob picks it up). `cargo xtask new <name>
  --standalone <dir> [--git <url> --rev <r>]` creates a project **outside**
  this repo: its own workspace, `game/` plus a `pc/` host on
  `trino-runner-pc`, starter assets and an AGENTS.md. The engine comes in as
  path or git deps (`templates/standalone/`; manifests are `*.tmpl` so
  cargo's git scan ignores them). Console packaging of standalone games is
  still done in this repo (BACKLOG P1). `release.yml` tags new
  workspace versions on main and publishes editor binaries + demo
  `.z64`/`.3dsx` + SHA256SUMS.
- **Editor two-way file sync** (`crates/editor/src/level_editor.rs` + the
  file watcher in `main.rs`): the **Level** tab paints the platformer's
  ASCII tilemap; every stroke saves immediately to
  `examples/platformer/src/level1.txt`, and external writes to that file or
  to `scenes/*.scene.ron` (AI agents, other tools) reload live in the UI —
  the file is the source of truth, with an echo guard so the editor's own
  saves don't bounce. A dirty scene is protected: external scene changes are
  logged, not force-loaded, until saved. Dev hook: `TRINO_EDITOR_TAB=level`
  opens with the Level tab focused (used for screenshots).

- **Engine services** (October 2026 pass, formats in
  `docs/adr/0005-backlog-pass-formats-and-services.md`):
  - **Bitmap text**: `[fonts.*]`, TFNT, `Renderer::draw_text`, `TextBuf`.
  - **Platform blobs** (`[blobs.*]`, `Platform::blob`).
  - **Save data** (`save_read/write`): framed, EEPROM on N64, SD on 3DS.
  - **Baked scenes** (`[scenes.*]` → `TSCN`, `BakedScene`): levels as data on every

  - **Collision**: `collider` component, `core::physics`.
  - **Runtime entities**: `EntityStore<N>`.
  - **Clip crossfade**: `AnimRef::blend_to`.
  - **Opt-in smooth skinning**: `skinning = "smooth"`, TMDL `SKW2`.
  - **Billboards and particles**: `draw_billboard`, `ParticleSystem`.
  - **Distance LOD**: `model.lod`.
  - **Positional audio**: `play_sound_with`, voices, stingers,

  - **Portal/cell visibility**: `core::vis`, `vis` component,
    `draw_nodes_in`/`draw_in`.

  Each one has a step in `castle64::selftest`, run on PC, in ares and in Azahar.
- **Editor additions**:
  - **Budget HUD** in the Game view.
  - **Play here**: the scene runs inside the Game view (Ctrl+Shift+P, Esc).
  - **Selection and arrangement**: multi-select and box select, the Arrange menu

draws are the levers. The ordered execution plan is `docs/plans/n64-throughput.md`.

## The one inviolable rule: dependency direction

```
game ──► core ◄── platform-{pc,n64,3ds}          apps glue them together
```

- `trino-core` must have **zero dependencies** and stay `no_std`.
- Game crates depend only on `trino-core` (+ `trino-game-api`). No external crates —
  that is what makes games portable to all three consoles by construction.
- Platform crates may use external crates but, within the workspace, only `trino-core`.
- libdragon/ctru/wgpu types must **never** appear in `core` or game code.

This is enforced by `xtask/tests/dep_graph.rs`, which runs in `cargo test --workspace`
and fails CI. If you add a crate, that test decides what it may depend on by name:
`trino-platform-*` and `trino-game*` prefixes carry rules.

## Design ceiling: the N64

If a feature cannot work on the N64, the engine does not expose it. There are no free
shaders: the pipeline is picked by `Material::{Sprite, VertexLit}` and a 3D surface is
plain data (`ModelParams`: tint, emissive, `Shading::{Gouraud, Flat, Unlit}`,
double-sided, animation pose) evaluated by the engine's own per-vertex T&L. `Caps` in
`crates/core/src/caps.rs` encodes per-console budgets (N64 TMEM = 4 KB); PC strict mode
validates content against them at development time.

## Commands

Everything goes through xtask (alias in `.cargo/config.toml`):

```
cargo xtask build pc      # compile the PC app
cargo xtask run pc        # build + launch (TRINO_SMOKE_FRAMES=60 auto-exits, for CI)
cargo xtask test          # full workspace test suite (same as CI); --bless regens goldens
cargo xtask assets pc     # bake assets into target/assets/pc
cargo xtask watch pc      # live-reload session (code dylib + assets)
                          #   --game <crate> picks the game dylib to rebuild
                          #   (default: castle64; must match apps/pc)
cargo xtask editor        # launch the visual editor
cargo xtask gen-assets    # regenerate sample masters (dev utility)
cargo xtask build n64     # ROM via Docker toolchain -> target/n64/trino.z64
cargo xtask run n64       # build + open in ares (ares-v148/ at repo root)
cargo xtask test n64      # build test ROM + assert ISViewer TRINO_TEST_PASS
cargo xtask watch n64     # rebuild ROM + relaunch ares on save
cargo xtask build 3ds     # .3dsx via local devkitPro -> target/3ds/trino.3dsx
cargo xtask run 3ds       # build + open in Azahar (auto-detected)
cargo xtask test 3ds      # build test app + assert magic strings (Azahar log)
cargo xtask watch 3ds     # rebuild .3dsx + relaunch Azahar on save
cargo xtask new <name>    # scaffold a game crate under examples/
cargo xtask scene check   # validate scenes/prefabs/materials (text-first loop)
cargo xtask scene export <scene.ron> <out.rs>   # scene -> no_std Rust data for games
cargo xtask model inspect <file> [--json]       # bake a model like the engine; art gate
cargo xtask agents sync   # mirror .agents/skills/ into .claude/skills/ (check: agents check)
cargo xtask new <name> --standalone <dir> [--git <url> --rev <r>]   # project outside this repo
cargo xtask emulators setup ares|azahar          # headless ares image / pinned Azahar AppImage
cargo xtask test n64 --bless                     # rewrite the ares golden frame + N64 perf ceilings (review!)
cargo xtask test 3ds --bless                     # rewrite the Azahar golden frame (review the PNG!)
TRINO_BLESS=1 cargo test -p xtask --test perf_budget   # rewrite the T&L work baseline (review the TOML!)
cargo xtask build 3ds --selftest && cargo xtask test 3ds --no-build   # CI's build/boot split
cargo xtask blender smoke                        # Blender toolkit end to end (needs Blender)
```

Run modes: `TRINO_SCENE=scenes/x.scene.ron cargo run -p trino-app-pc` plays a scene
(reloads when the scene, prefabs or materials change; model edits need a restart);
`TRINO_GAME=showcase cargo run -p trino-app-pc` runs the exported-scene game; editor hooks (`TRINO_EDITOR_SCREENSHOT`, `_SELECT`, `_TAB`, `_ECHO_LOG`,
`_SCENE`) are listed in the `editor` skill.

Before committing, always run the CI-equivalent locally:

```
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

## Testing conventions

- Every feature ships with tests in the same PR. No exceptions — the roadmap lists the
  expected tests per phase.
- Unit tests live next to the code (`#[cfg(test)]`). `core` uses
  `#![cfg_attr(not(test), no_std)]` so tests can use std.
- Golden-image tests (Fase 1+) live in `tests/golden/`; regenerate only via
  `cargo xtask test --bless` and review the diff in the PR. Performance work must leave
  goldens byte-identical.
- Guard tests: `dep_graph`, `agents_sync` (skill mirrors), `scene_codegen` (exported
  scene drift), `showcase_render` (runtime == codegen pixels). See the `test-all` skill.
- Console tests report through debug channels — ISViewer magic strings on
  N64 (`apps/n64/src/lib.rs::run_self_test`), `svcOutputDebugString` on 3DS
  (`apps/3ds/src/main.rs::run_self_test`, read from Azahar's log file).
  `cargo xtask test n64|3ds` runs them locally; CI boots both (the ares Docker
  image, and the pinned Azahar under Xvfb).
- Every engine service has a step in `castle64::selftest`, the same code on
  PC (`xtask/tests/engine_checks.rs`), in ares and in Azahar. A new
  console-visible feature adds a step there.
- Emulator golden: `tests/golden/n64/showcase.png` is compared pixel-exactly
  by `test n64`. A renderer change on the N64 path re-blesses it
  (`--bless`), and the PNG diff gets reviewed like any golden.
- 3DS golden: `tests/golden/3ds/castle64_hub.png`, compared within a
  tolerance by `test 3ds` (Azahar's pixels depend on the host OpenGL);
  `n3ds_parity` holds the PC's N3ds look to it.
- Performance is gated: `xtask/tests/perf_budget.rs` pins castle64's T&L
  work per scene (`tests/perf/castle64_work.toml`), and `test n64` pins
  the emulated frame cost (`tests/perf/castle64_n64.toml`). Quote the
  scene table before/after for T&L or backend changes, and bless on
  purpose. `bench_tnl` measures host CPU only.

## Toolchain notes

- Workspace builds on **stable** (see `rust-toolchain.toml`). Console target
  builds run on **nightly** with `-Zbuild-std=core,alloc`: the N64 against
  `platforms/n64/mips-nintendo64-none.json` (plus `-Zjson-target-spec`), the
  3DS against the built-in `armv6k-nintendo-3ds` — never change pins or the
  target spec casually; they are verified combinations.
- Linux: the PC crates need `pkg-config` + ALSA headers (`libasound2-dev`).
- Console code is `cfg`-gated on the host, so `cargo check` there proves nothing —
  type-check for real with nightly + `-Zbuild-std` (commands in the `test-all` skill).
- Windows: N64 builds need Docker reachable from WSL2 (Docker Desktop optional —
  a plain in-WSL dockerd works; xtask calls `wsl docker ...`). 3DS builds need
  a local devkitPro install (`3ds-dev` packages). PC development needs nothing
  beyond Rust.

## Pitfalls

- **N64 FFI: no scalar float after an integer argument.** Rust is o32 and libdragon
  is o64, so the float arrives as garbage. Pass 16.16 fixed point (`u32`) or a
  pointer (ADR 0005 §6).
- **N64 z precision is 16-bit.** Coplanar surfaces need centimetres of separation at
  gameplay distances, or they z-fight on the console but not on PC (Depth32Float).
  The ares golden catches it.
- **Azahar's file log flushes only on errors.** The harness turns on
  `instant_debug_log`, so don't remove it.
- **N64 link: Rust's `compiler_builtins` defines `memcpy/memset/memmove/memcmp`
  as weak generic loops and wins over newlib** once its object is linked.
  `-Wl,-u,<sym> -Wl,-lc` ahead of the staticlib fixes it. The gcc driver
  silently drops a repeated plain `-lc`, so it must be `-Wl,-lc`. Read the map's
  memory section, not "Discarded input sections". `check_mem_symbols` guards it.
- **Code layout moves N64 timings ~20% per stage** (ares is reproducible per ROM,
  but I-cache conflicts are not). Never claim a small win from one build: A/B on
  identical code and judge on the scene table, not on a synthetic bench.
- **3DS: never draw 3D with `C2D_DrawTriangle`.** It takes one depth per triangle,
  so big floors cover what stands on them. Everything goes through
  `trino_3d_draw` (per-vertex depth).
- **The N64 main stack is 64 KB and an overflow is silent** (memory corruption, random
  hangs; interrupts push onto it too). A ~22 KB struct built by value (`ShowcaseGame`)
  overflowed it in the self-test. `Box::new(big())` still builds the temporary in the
  caller's frame, so put such steps in their own `#[inline(never)]` function.
  `check_stack` fails the self-test above 60 KB.
- **Renderer state (camera, light) outlives frames and games.** A game that never
  calls `set_light` inherits the last one. On consoles the self-test's showcase
  fog leaked into castle64. Set both every frame.
- **`Caps::N64.max_tris_per_frame` is not the CPU T&L budget.** A 30 fps frame
  affords roughly 550–650 source triangles today, fewer with many draws. Use
  `model inspect`'s N64 cost estimate. Strict mode enforces
  `Caps::max_3d_us_per_frame` (N64: 50 ms estimated).
- **glTF COLOR_0 is linear.** The bake converts it to display sRGB, so write linear
  values (the generators use `color0_linear`). Before 2026-10-13, Blender-painted
  colors baked much darker.
- **Hidden faces still cost N64 CPU.** A face buried inside another part, or a back
  face, pays its transform. Build models from visible faces only (`blender-asset`).
  Don't union parts with a boolean: it cuts holes and adds triangles.
- **Template manifests are `Cargo.toml.tmpl`.** A placeholder `Cargo.toml` anywhere in
  the repo breaks every git-dependency user, because cargo scans the whole repository.

- Do not add dependencies to `trino-core` — the dep-graph test will fail, and the crate
  must compile for MIPS bare metal.
- Screen space is X-right, **Y-down**, origin top-left; stick input is Y-up.
- `SpriteId`/`SoundId` handles are stable across live reloads (derived from logical
  asset paths). Never cache anything keyed on their numeric value being contiguous.
- Hot-reload boundary: no generics in exports, no statics in the game dylib (they reset
  on reload), no `TypeId` across the boundary, and state layout must not change between
  reloads (that requires a restart). Exports are generated by
  `trino_game_api::export_game!` — see `crates/game-api/src/lib.rs`. `cargo xtask watch pc`
  deliberately watches only `examples/`: a change to `crates/core` can change type
  layouts, and swapping a dylib across a layout change is UB.
- Game crates use `#![cfg_attr(any(target_os = "none", target_os = "horizon"), no_std)]`
  (N64 is `none`, 3DS is `horizon`) — std exists on PC only for the dylib's
  panic handler; game code must never call std APIs.
- Console FFI goes **only** through the C shims (`crates/platform-{n64,3ds}/shim/`
  + the matching `src/ffi.rs`, kept in pairs), and every entry must stay
  within ≤4 scalar/pointer args, no by-value structs, no variadics, no 64-bit
  values across the boundary. On the N64 this is a hard ABI requirement
  (Rust is o32, libdragon is o64 — `docs/adr/0002-n64-abi-o32-staticlib.md`);
  on the 3DS it is convention (citro2d is static-inline C, and symmetry keeps
  the backends maintainable). Never call libdragon/libctru/citro2d from Rust.
- Authored-content paths: compare watcher paths **without** a `./` prefix
  (`Library::logical_for_file` normalizes; use root `Path::new("")`). Ignore inotify
  *access* events — reading a file emits them and would loop reloads.
- Rotations are **degrees** in RON files and **radians** in `trino_core`. The core's
  sin/cos/atan2 are fast approximations (deterministic across consoles); never
  round-trip authored values through them in tools (the gizmo uses std math).
- `ModelParams` grows: construct it with `ModelParams::tinted(c)` or
  `ModelParams { .., ..ModelParams::DEFAULT }`, never a bare struct literal.
- TMDL is extensible by **sections** (`BNDS`, `SKEL`, `ANIM`; unknown tags are skipped):
  add data as a new section instead of changing the base layout.
- Rigid skeletons: ≤ 32 joints (`MAX_JOINTS`, stack-allocated), parents before children,
  one skin per file, heaviest weight wins.
