# Trino — Agent Guide

Trino is a Rust game engine targeting **Nintendo 64, Nintendo 3DS, PC and the Web** from a
single codebase, with a visual editor, console-simulation modes, live reload and emulator-based
testing. This file is the canonical entry point for **any** AI agent (Claude Code, Codex,
Gemini CLI, Cursor, Copilot, …) and a good one for humans.

What to build next (ranked): `docs/BACKLOG.md`. Guides by topic (architecture, assets,
platforms, hardware): `docs/README.md`. Historical plans the engine was first built from,
2D-first and since outgrown: `PLANO_EXECUCAO_TRINO.md` (phases and acceptance criteria) and
`PLANO_ENGINE_TRINO.md` (original rationale), both in Portuguese.

## Working with AI agents (vendor-neutral)

- **Instructions:** this file. `CLAUDE.md` and `GEMINI.md` only import it;
  `.github/copilot-instructions.md` points here. Codex and Cursor read `AGENTS.md` natively.
- **Skills:** canonical in `.agents/skills/<name>/SKILL.md` (the open Agent Skills format,
  read natively by most agents). `.claude/skills/` is a **generated byte-identical mirror**
  for Claude Code — edit only `.agents/skills/`, then `cargo xtask agents sync`
  (`xtask/tests/agents_sync.rs` fails CI on drift and on skills missing from this table).
- **Everything is text and hot-reloads both ways:** scenes, prefabs, materials and fake
  objects are RON files the editor reads and writes; an agent edits the same files and a
  running editor / scene player updates live. Validate with `cargo xtask scene check`,
  art with `cargo xtask model inspect`, and *look* with the editor's screenshot hook.

| Skill | Use it for |
|---|---|
| `add-asset` | sprites, sounds, music, models, fake objects, materials → manifest, bake, verify |
| `blender-asset` | modeling / coloring / rigging / animating a model in Blender for Trino's real limits; export + `model inspect` gate |
| `scene-authoring` | writing scenes, prefabs, materials as text; `scene check`; exporting scenes to console code |
| `editor` | running the editor, screenshot/selection/log hooks for agents, editor code map |
| `build-n64` | ROM build via Docker, N64 pipeline troubleshooting |
| `build-3ds` | .3dsx build via devkitPro, 3DS pipeline troubleshooting |
| `build-web` | the browser build (wasm, WebGPU/WebGL2): build, run and test for the Web, the Playwright harness, KTX2, the WebGL2 limits |
| `run-emulator` | ares / Azahar runs, emulator test harness, watch loops |
| `hardware` | real consoles: SummerCart64 / EverDrive 64 (USB) and 3DS (3dslink) deploys with the debug log in the terminal, Luma3DS gdb |
| `test-all` | the CI gates + guard tests, console type-checks, T&L benchmark |
| `engine-feature` | adding/changing an engine service or format end to end: all backends, self-test step, docs, the closing knowledge loop |
| `n64-performance` | per-stage/per-model N64 frame cost (emulated, ares), perf gates, the calibrated cost model, before/after workflow, what worked |
| `ci` | the GitHub Actions jobs, why they're shaped that way, replicating a job locally, debugging red runs |
| `new-project` | `cargo xtask new` (in-repo or `--standalone`), maintaining the templates and `trino-runner-pc` |

**Knowledge loop:** before reporting a task done, write what it taught you into the
skill that owns that kind of work. A trap also gets a line under Pitfalls below. Create a
new skill when none fits. Then run `cargo xtask agents sync`. The steps are in
`engine-feature` › Closing. A skill that turns out wrong gets fixed in the same session.

## Current state

**All 9 roadmap phases (0–8) implemented.** Working today:

- PC rendering (wgpu, console-sim resolutions, golden tests): low-poly 3D with 2D
  (sprites, text, rectangles, billboards) in the same renderer and frame; audio, input.
- Asset pipeline: `assets/manifest.toml` + shared masters + per-platform overrides →
  `cargo xtask assets pc`. Handles = fnv1a(logical path), stable across reloads.
- Live reload: `cargo xtask watch pc` — saving a master rebakes + re-uploads it live;
  saving game source rebuilds the dylib and hot-lib-reloader swaps functions under the
  running state (`apps/pc` feature `reload`).
- **Editor** (`cargo xtask editor`, `crates/editor`): dark themed dockable UI (Inter +
  Phosphor icons) — **Scene view** (real `PcRenderer` at panel resolution, orbit camera,
  z-buffered grid, click picking, move/rotate/scale **gizmo** with snapping, planar
  handles and a view ring, Unity-style navigation (MMB pan, Alt+RMB dolly, RMB-held
  WASD/QE fly), a Blender-style axis widget (drag to orbit, click an axis twice to flip,
  centre or `5` for a near-orthographic view), drag-and-drop from Assets), **Game view**
  (scene camera at N64/3DS/PC resolution and look), Hierarchy tree (parenting by drag,
  rename, visibility, prefab instances), Inspector (components, inline material editing,
  prefab overrides, scene environment), Assets browser (rendered thumbnails), Console,
  toasts, status bar. Snapshot **undo/redo**, copy/paste entities **as RON** (Ctrl+C/V —
  round-trips through any AI chat), keyboard shortcuts (F1). **Play** runs the open
  scene (`TRINO_SCENE`, live reload) or the game, in a separate process. Every UI action
  writes a text file.
  Agent hooks: the `editor` skill.
- **Content formats** (`trino-scene` crate, versioned RON, hot-reloaded):
  scenes v3 (`scenes/*.scene.ron`: nested entities, 3D transforms in degrees, models +
  materials + animation clip, sprites, tags, prefab instances, environment = camera,
  colored light, fog); **prefabs** (`prefabs/*.prefab.ron`: linked instances,
  per-instance overrides, unpack, nesting with cycle detection — Blender-style);
  **materials** (`assets/materials/*.material.ron`: tint, `Gouraud|Flat|Unlit`,
  emissive, double-sided — all evaluated by the software T&L, so identical on every
  target). v1/v2 scenes migrate on load. **Per-platform variants** (scene v3, ADR 0009):
  an entity's `platforms` block swaps the model, material or scale, hides it or leaves it
  out on `pc`, `n64` or `n3ds`; `resolve_for`, `scene export --platform`, each
  platform's `[scenes.*]` bake and the editor's Game view apply them. `cargo xtask scene check` validates;
  `cargo xtask scene export` turns a scene into `no_std` Rust data
  (`trino_core::SceneNode`) for consoles — `examples/showcase` is the editor's demo
  scene that way (runs on PC with `TRINO_GAME=showcase`, type-checks for N64/3DS), and
  `xtask/tests/showcase_render.rs` proves runtime and exported scenes render
  pixel-identically. ADR: `docs/adr/0004-authored-content.md`.
- **Fake objects**: parametric placeholder models (`*.prim.ron`: box, sphere, cylinder,
  cone, capsule, plane, ramp, torus; size, colors/gradient, pivot, segments) baked to
  TMDL like any glTF — usable on every target immediately; point the manifest `file` at
  the real `.glb` later and every reference stays (same handle). Editor: Create › Fake
  object (Shift+A, live preview), live parameter editing in the Inspector.
- **Rigid animation**: glTF node animations / skins bake into a TMDL skeleton (≤ 32
  joints, each vertex follows one joint — the N64-era limb model) + clips sampled at
  `anim_fps`; `ModelParams::anim` poses a draw; evaluated in `trino_core` on the stack,
  so all three targets animate with no backend code. `cargo xtask model inspect` is the
  art acceptance gate (tris, joints, clips, bounds, N64 budget and calibrated
  N64 cost per draw).
- **N64**: `cargo xtask build n64` produces `target/n64/trino.z64` (Docker
  toolchain image + C shim + Rust staticlib — ABI story in
  `docs/adr/0002-n64-abi-o32-staticlib.md`); `run n64` opens it in ares
  (expected at `ares-v148/` in the repo root, gitignored); `test n64` boots a
  test ROM and asserts on ISViewer magic strings (`TRINO_TEST_PASS/FAIL`), on
  a pixel-exact **emulator golden** (`tests/golden/n64/showcase.png`, from a
  framebuffer dump; `--bless` rewrites it) and on **perf gates**: per-scene,
  per-stage, per-model frame cost in emulated N64 time (`TRINO_PERF_SCENE` /
  `TRINO_PERF_MODEL`), whose T&L work counters must equal the PC baseline and
  whose times must stay under `tests/perf/castle64_n64.toml`. `TRINO_ARES=docker` runs ares from the
  `docker/ares` image (`cargo xtask emulators setup ares`) — what CI does.
  `watch n64` rebuilds + relaunches on save. Skills: `build-n64`, `run-emulator`.
- **N64 look on PC**: the `SimProfile::N64` renderer emulates the console
  output — 3-point filtering + RGBA5551 quantization with the RDP magic-square
  dither (`TRINO_LOOK=off|n64` overrides). Strict mode (`TRINO_STRICT=1` or
  `PcRenderer::set_strict`) panics with an actionable message when content
  busts the profile's `Caps`. The 16-bit write follows the RDP's own rule
  (angrylion `dither.c`), and a **VI dedither pass** runs at `end_frame`
  (`set_vi_dedither`). The N64 shim enables the same dither and VI filter, so
  PC and console match: `xtask/tests/n64_parity.rs` compares the PC frame
  with the ares golden (mean diff about 2.5/255).
- **3DS**: `cargo xtask build 3ds` produces `target/3ds/trino.3dsx` — all
  local (devkitPro install auto-detected; built-in `armv6k-nintendo-3ds`
  Tier 3 target, C shim over libctru + citro2d in
  `crates/platform-3ds/shim/`); `run 3ds` opens it in Azahar (auto-detected
  or `$TRINO_AZAHAR`, or the pinned AppImage from `cargo xtask emulators
  setup azahar`); `test 3ds` asserts the TRINO_TEST_* magic strings by
  tailing Azahar's log (`svcOutputDebugString` channel; the harness seeds or
  patches Azahar's config) and compares a castle64 frame with
  `tests/golden/3ds/castle64_hub.png` within a tolerance. All 3D is drawn
  by citro3d with **per-vertex depth** (`trino_3d_draw`). `build 3ds --selftest` + `test 3ds --no-build`
  split build and boot, as CI does. `watch 3ds`
  rebuilds + relaunches on save. `--accurate-timing` (or `TRINO_AZAHAR_GPU_TIMING=1`)
  turns on Azahar's "Simulate 3DS GPU timings" for one session and restores the
  user's setting afterwards (`docs/HARDWARE.md`). The `SimProfile::N3ds` PC renderer samples
  sprites bilinearly (the 3DS GPU default). Skills: `build-3ds`,
  `run-emulator`.

- **Legacy 2D examples** (`examples/platformer`, `examples/hello-sprite`): from
  the engine's first, 2D-only phases. Not the model for new games (that is
  castle64 and `cargo xtask new`); a redesigned 2D sprite/tile system is a
  future release (BACKLOG P2 #14). Don't delete or rename them: the hot-reload
  E2E builds hello-sprite, and the `platformer_scene` PC golden, the
  `hero_shot`/`record_gif` media tools and the editor's Level tab use the
  platformer. The platformer:
  tilemap + AABB physics from `trino_core::{tilemap,collide}`
  (ASCII levels, zero-alloc parse, substepped collision — deterministic
  across targets, verified by unit tests and the console self-tests), coins,
  goal, camera with bounds, chiptune music loop + SFX. Music flows through
  the whole pipeline (`[music.*]` in the manifest → TSND on PC, wav64
  `--wav-loop` on N64, looped ndsp wavebuf on 3DS). `hello-sprite` is
  the minimal sprite example (the hot-reload E2E builds it standalone).
  Platformer media (`docs/media/platformer.*`): `cargo test -p xtask --test
  hero_shot|record_gif -- --ignored`. The README's hero GIF is castle64's
  (`docs/media/castle64.gif`).
- **castle64** (`examples/castle64`, the 3D showcase and the default game in
  all three `apps/*`): SM64-style hub + 3 platforming stages + throne room.
  Own 3D AABB physics (axis-resolved with a contact skin — `physics.rs`),
  inertial movement with variable-height jumps, an articulated 5-part purple
  player (torso/arms/legs pivoted at shoulders/hips, real walk cycle),
  patrol boars with stomp kills, lava, moving platforms that carry the
  player, an orbit camera clamped by raycast, tinted doors and a HUD with
  generated digit sprites. The characters and doors are built in Blender by
  `tools/blender/castle64_models.py` (`cargo xtask blender castle64`), with
  only the faces a camera can see. The castle entrance is KayKit's Dungeon
  Remastered doorway (CC0) rebuilt at 75 triangles. The original 1068-triangle
  file stays as the asset pipeline's textured multi-primitive fixture. A
  deterministic waypoint bot (`castle64::bot`) plays the entire game in the
  PC test suite and a full stage inside the ares/Azahar self-tests.
  Generated masters regenerate via `cargo xtask gen-assets`
  (`xtask/src/castle64_assets.rs`); screenshots/GIF via
  `cargo test -p xtask --test c64_shots|c64_gif -- --ignored`.
- **3D (`draw_model`)**: engine-side software T&L (`trino_core::render3d` —
  see `docs/adr/0003-software-tnl-3d.md`; on the N64 most draws run it on the RSP
  instead, ADR 0007, and this CPU path stays the reference everywhere): glTF masters bake to the portable
  TMDL format (`[models.*]` in the manifest); the core transforms, lights
  (gouraud, directional + ambient), culls and depth-sorts on the CPU with
  deterministic f32 (own no_std sin/cos/sqrt); backends only rasterize
  screen-space colored triangles (`rdpq_triangle` shade / a citro3d vertex
  buffer / a wgpu vertex-color pipeline interleaved with sprites). `set_camera` +
  `set_light` (colored directional + ambient + distance fog) + `draw_model` /
  `draw_model_matrix` (hierarchies) on all three targets — `ModelParams` is the
  per-draw surface: tint (locked doors, glow pulses — no separate baked meshes),
  emissive, `Shading::{Gouraud, Flat, Unlit}`, double-sided, animation pose.
  Meshes outside the frustum are culled whole from a baked bounding sphere; a
  per-draw vertex cache transforms/lights shared vertices once (CPU cost is
  tracked by `xtask/tests/bench_tnl.rs`). Strict mode enforces
  `max_tris_per_frame`. The (legacy) platformer shows a spinning cube.
  Triangles are clipped against the near plane + a 1.5x guard-band frustum
  (bounded coordinates — RDP fixed-point safe); in fogged, textured or translucent
  draws, edges spanning > 3 units of view depth are bisected (`split_policy`: opaque
  draws don't need it, the per-vertex z is affine on screen); `math3d` ships
  deterministic `sin/cos/sqrt/atan2`.
  Occlusion is **z-buffered** on every target (per-vertex normalized depth
  in `ScreenTri::z`: wgpu depth buffer on PC, RDP hardware z-buffer on N64,
  per-vertex depth through citro3d on 3DS) — interpenetrating geometry
  resolves per pixel; the `occlusion` self-test step proves it on every target. Consecutive `draw_model` calls still form a depth-sorted batch
  (tie-break + blending order; flushed on sprite draws, camera changes and
  `end_frame`). **Textured 3D**: one texture per draw (TMDL `TXUV`/`TXID`,
  `ModelParams.texture`, material `texture`), on all three targets.

- **Scaffolding + release**: `cargo xtask new <name>` renders
  `templates/new-game/` into `examples/<name>` (game crate + its own
  AGENTS.md; the workspace glob picks it up). `cargo xtask new <name>
  --standalone <dir> [--git <url> --rev <r>]` creates a project **outside**
  this repo: its own workspace, `game/` plus a `pc/` host on
  `trino-runner-pc`, starter assets and an AGENTS.md. The engine comes in as
  path or git deps (`templates/standalone/`; manifests are `*.tmpl` so
  cargo's git scan ignores them). Its console builds use `trino.toml` and
  need a local engine checkout (ADR 0008, below). `release.yml` tags new
  workspace versions on main and publishes editor binaries + demo
  `.z64`/`.3dsx` + SHA256SUMS.
- **Editor two-way file sync** (`crates/editor/src/level_editor.rs` + the
  file watcher in `main.rs`): the **Level** tab (legacy, tied to the 2D
  platformer) paints the platformer's ASCII tilemap; every stroke saves immediately to
  `examples/platformer/src/level1.txt`, and external writes to that file or
  to `scenes/*.scene.ron` (AI agents, other tools) reload live in the UI —
  the file is the source of truth, with an echo guard so the editor's own
  saves don't bounce. A dirty scene is protected: external scene changes are
  logged, not force-loaded, until saved. Dev hook: `TRINO_EDITOR_TAB=level`
  opens with the Level tab focused (used for screenshots).

- **Engine services** (October 2026 pass, formats in
  `docs/adr/0005-backlog-pass-formats-and-services.md`):
  - **Bitmap text**: `[fonts.*]`, TFNT, `Renderer::draw_text`, `TextBuf`.
  - **Platform blobs** (`[blobs.*]`, `Platform::blob`).
  - **Save data** (`save_read/write`): framed, EEPROM on N64, SD on 3DS.
  - **Baked scenes** (`[scenes.*]` → `TSCN`, `BakedScene`): levels as data on every
    target.
  - **Collision**: `collider` component, `core::physics`.
  - **Runtime entities**: `EntityStore<N>`.
  - **Clip crossfade**: `AnimRef::blend_to`.
  - **Opt-in smooth skinning**: `skinning = "smooth"`, TMDL `SKW2`.
  - **Billboards and particles**: `draw_billboard`, `ParticleSystem`.
  - **Distance LOD**: `model.lod` — a chain of lighter meshes, an **impostor** and a cull,
    each level with its own start per platform (`At(d)` / `Never`); TSCN v2.
  - **Impostors** (2026-10-15, ADR 0009): `trino_core::Impostor` (a `TIMP` table + an atlas
    sprite) draws a model as one billboard, the view chosen by the camera's yaw; baked by
    the engine itself (`cargo xtask impostor`, the editor's model inspector — same files),
    CI4 within TMEM on the N64; `impostor` self-test step on PC, ares and Azahar.
  - **Positional audio**: `play_sound_with`, voices, stingers,
    `Listener`/`spatialize`, the `sound` component plus `Ambience`.
  - **Portal/cell visibility**: `core::vis`, `vis` component,
    `draw_nodes_in`/`draw_in`.
  - **Color slots + per-draw palette** (2026-10-15): glTF `_SLOT` → TMDL `SLOT`,
    `ModelParams::palette` recolors slots 1..=4 of one model per draw (a crowd from
    one character). CPU T&L on every target; never on the N64 RSP. Its self-test
    step passes on PC, in ares and in Azahar.

  Each one has a step in `castle64::selftest`, run on PC, in ares and in Azahar.

- **Performance & stability pass** (2026-10-13, `docs/BACKLOG.md` › Done, ADR
  `docs/adr/0006-performance-and-visual-gates.md`):
  - **Measurement**: N64 per-stage/per-model profiling (`trino_core::perf`) over five
    deterministic `castle64::perf` scenes.
  - **Gates**: exact T&L work counters on PC (`perf_budget`) and in the ROM; N64
    time ceilings.
  - **Cost model**: calibrated `N64_COST` in `model inspect` and the editor HUD.
  - **N64 fixes**: hub render 640 → 175 ms. T&L scratch per draw, sort keys, newlib
    `mem*`.
  - **Content + T&L follow-up**:
    - castle64's characters and doors rebuilt in Blender with only their visible
      faces (`cargo xtask blender castle64`);
    - bake: COLOR_0 is linear, vertex-cache order;
    - back faces are rejected before clipping and splitting.

    Hub frame 174 → 76 ms; sky-tower 31 ms (≈ 32 fps). Every golden is identical
    under the T&L change.
  - **3DS fixes**: per-vertex depth (floors no longer cover characters).
  - **castle64 fix**: the game declares its own light.
  - **Visual checks**: a 3DS golden frame and `n3ds_parity`.
  - **Stability**: the N64 self-test stack overflow is fixed, and a guard
    (`check_stack`) catches the next one.

- **N64 throughput plan** (2026-10-13, `docs/plans/n64-throughput.md`, BACKLOG ›
  Done): castle64 frame, emulated N64 ms, hub 76.1 → 39.4, green-hills 37.3 → 19.8,
  lava-land 49.1 → 21.7, sky-tower 31.2 → 18.9, throne 43.4 → 16.0. The four stages
  now run at 46–62 fps.
  - **T&L constant factors**: `TnlContext` per camera/light, backend-owned
    `TnlScratch`, meshes parsed once (`MeshLayout`), vertex fetch via `as_chunks`,
    tint quotients per draw, per-path T&L functions with a `#[cold]` clip,
    reciprocals, model-space lighting. All golden-identical.
  - **Content/renderer**: castle64 coins are billboards; depth splits only where
    they matter (`split_policy`).
  - **Tools**: `micro-*` perf scenes for fixed costs; `Caps::max_3d_us_per_frame`
    in strict mode; `model inspect` and the editor report N64 time;
    `N64_COST` recalibrated.

- **N64 RSP T&L** (ADR 0007, `crates/platform-n64/shim/rsp_trino.S`).
  - Most N64 draws run on Trino's own rspq overlay instead of `tessellate`: static,
    opaque, untextured, unclipped Gouraud/Unlit draws (`trino_core::render3d::
    rsp_eligible`).
  - Fixed-point transform, model-space light, libdragon's RSP triangle setup.
  - Same ROM: hub 38.0 → 13.1 ms, every stage 7–8 ms (vsync caps at 60 fps).
  - Gated by an oracle, CPU-vs-RSP pixel checks, the work split (`rsp_draws`) and
    the `castle64_hub` N64 golden.
  - **Since #69 (2026-10-18, ADR 0018):** four overlays from the same source:
    `rsp_trino` (white), `rsp_trino_color` (colored light, emissive, double-sided,
    per-vertex fog), `rsp_trino_tex` (textured) and `rsp_trino_water` (swell, Fresnel,
    glint, light and fog per vertex). Flat draws take flat copies; rigid skeletons a
    command per joint. A fogged, textured or water draw takes the RSP only where the
    CPU path would split no edge. `render3d::rsp_plan` is the rule every predictor
    calls. The showcase river went 286.6 → 75.2 ms and `micro-river` 19.6 → 10.5 ms
    (mean over 8 paddings).
  - **#69's second part (ADR 0018 §7):** ripples and rings on the water overlay, two
    vertices per pass, a static block per draw plus a frame block per material,
    streaming that wakes the RSP (`trino_rsp_flush`). `micro-river` 1.78 ms (its
    draws 0.94 ms of CPU, ~0.9 ms of RSP beside it) and `showcase-river` 26.2 ms in
    ares, gated at the issue's 1.2 / 33.3 ms (`perf::BUDGETS`). `N64_COST` prices
    water on the RSP apart (`RspWork`). Not yet measured on a real N64.

- **PC hardware T&L (2026-10-17/18, ADR 0016, GitHub #51):** the PC native profile
  transforms and lights most models on the GPU; the CPU T&L stays the reference.
  - **Instancing on every target:** `Renderer::draw_model_instances(model, &[Instance],
    &params)` and `draw_model_instances_with(.., &[Palette], ..)`. An `Instance` is a
    matrix, a tint multiplied over the call's (`(a·b + 127) / 255`) and a palette index
    (0 = the call's, `k` = `palettes[k - 1]`). The default loops over
    `draw_model_matrix`, so the N64 and the 3DS need no code. The `instancing` self-test

- **Two screens (2026-10-14, typed API 2026-10-15):** `trino_core::Screen`
  (`Top` = the main screen everywhere, `Bottom` = the 3DS touch screen).
  `Renderer::on_screen(Screen)` sends the next draws, **2D and 3D**, to a screen and
  returns `false` when they don't go there: the screen is missing (PC native, N64:
  skip the draws), or it is `Top` after the frame moved to the bottom. The order is
  the top first, then the bottom, once per frame, on every backend. Each screen has
  its own target, so draws are clipped to it, and its own projection: the T&L and the
  3DS shim's citro3d matrix switch to 320×240, so set a camera for the bottom. The
  camera is renderer state: a bottom-screen `set_camera` carries into the next
  frame's top unless the game sets the top's camera again, so set it every frame on
  each screen. A two-screen backend overrides `set_screen`, `screen()` and
  `second_screen` together, because the provided `on_screen` reads `screen()`. Also
  `screen()`, `screen_size(Screen)`, `read_screen_pixel(Screen, x, y)` (the
  self-test read-back of either screen) and the low-level `second_screen`/`set_screen(u8)`.
  `Platform::second_screen` is known at update time. Touch routing:
  `InputState::pointer_on(Screen)` (a 3DS touch is on `Bottom`, in its own pixels),
  so world picking asks for `Top` and never sees a touch. The PC's 3DS profile
  renders and presents both screens stacked, maps the mouse to either, and
  `present_preview`/`read_second_screen` capture them. The 3DS host dumps the touch
  screen as the next golden (`dump_framebuffer_bottom`). castle64 shows it: a map,
  counters with a 3D star, and touch buttons on the bottom screen (the
  `dual screen` self-test step, `castle64_hub_bottom.png`). The showcase's bottom
  screen (`examples/showcase/src/panel.rs`, GitHub #20) is a touch panel: live
  metrics (frame time from `dt`, `Renderer::stats` with the `tnl` counters) and
  buttons for the look (camera preset, scene/dusk light, fog, `set_texture_filter`,
  the animation clock), each also on a pad button (X, Y, B, Select, Start), so they
  work on one screen too. `showcase::panel::check_panel` reads it back on the PC's 3DS
  profile (`xtask/tests/showcase_panel.rs`, with mutations that must fail) and in
  Azahar (the `showcase panel` step, golden `showcase_bottom.png`).

    base) self-test a scripted match. The sim hash equals the PC's
    (`TRINO_SE_HASH`), and the template is checked against a frame budget and
    goldens in CI. `TRINO_GAME=solid-eleven cargo run -p trino-app-pc` plays it.

PC keyboard mapping: A/B = Z/X, X/Y = C/V, L/R = Q/E, Start = Enter,
Select = Right Shift, D-pad = arrows, stick = WASD; L2/R2/L3/R3 have no default key
(see `crates/platform-pc/src/input.rs`). Gamepads (gilrs): A/B/X/Y, L = LB+LT, R = RB+RT,
L2/R2 = LT/RT, L3/R3 = stick clicks, Start = Start+Guide, Select = Back+LS, both sticks
(`stick`, `right_stick`) and the analog triggers (`triggers`, 0..=1).
On top of it, `InputState::keys` (a 128-bit `trino_core::KeySet`) carries the whole PC
keyboard (`trino_core::Key`: letters, digits, F1–F12, arrows, Home/End/PgUp/PgDn/
Insert/Delete/Backspace, Shift/Ctrl/Alt/Super, Space/Enter/Escape/Tab and punctuation;
`=` also sets `Plus`, numpad 1–3/Enter/+/− alias the main row). Every key sets its bit,
bound keys too (Z sets `Key::Z` and presses A). The first 30 `Key`s keep their old
bit positions and `KeySet` has `&`/`|`/`!` and `== u32`, so code written for the old
`u32` (`now.keys & !prev.keys != 0`) still compiles. `InputState::pad` says a gamepad
was used this frame. Consoles: N64 C-left/C-down stay X/Y and the four C buttons are
also `right_stick`, Z is Select; New 3DS ZL/ZR = L2/R2 (`triggers` 0 or 1), C-stick =
`right_stick`.
Both the keys and the pad buttons can be **rebound** from the game: `Platform::input_info`
(gamepad support/connection, a pending rebind), `gamepad_name`, `binding_label`,
`rebind`, `cancel_rebind`, `reset_bindings` (PC only, `None`/no-ops on consoles).
`trino-runner-pc` applies them after the frame and keeps them in `<save_name>.input`
(text; `input::bindings_to_text`, one line per `BINDABLE` button; files from before
L2–R3 have 12 lines and still parse). The next bindable key or pad button pressed becomes
the binding, Escape cancels; keys with a fixed role (WASD and the shortcut keys: Esc,
Space, Tab, Delete, Backspace, F1–F8, 1–3, Page Up/Down, Home, R, T, =, −, Ctrl; and
Super, which the OS takes) are not bindable, so one press never does two things. Without the `gamepad` feature (or a working pad layer)
`GamepadStatus::Unsupported` and keyboard rebinding still works.

## The one inviolable rule: dependency direction

```
game ──► core ◄── platform-{pc,n64,3ds,web}      apps glue them together
           ▲
           └──── render-wgpu ◄── platform-{pc,web}
```

- `trino-core` must have **zero dependencies** and stay `no_std`.
- Game crates depend only on `trino-core` (+ `trino-game-api`). No external crates —
  that is what makes games portable to all three consoles by construction.
- Platform crates may use external crates but, within the workspace, only `trino-core` and
  `trino-render-wgpu` (the renderer the PC and the Web share, itself on `trino-core` only).
- libdragon/ctru/wgpu types must **never** appear in `core` or game code.

This is enforced by `xtask/tests/dep_graph.rs`, which runs in `cargo test --workspace`
and fails CI. If you add a crate, that test decides what it may depend on by name:
`trino-platform-*` and `trino-game*` prefixes carry rules.

## Design ceiling: the N64

If a feature cannot work on the N64, the engine does not expose it. There are no free
shaders: the pipeline is picked by `Material::{Sprite, VertexLit}` and a 3D surface is
plain data (`ModelParams`: tint, emissive, `Shading::{Gouraud, Flat, Unlit}`,
double-sided, animation pose, a palette for color slots) evaluated by the engine's own per-vertex T&L. `Caps` in
`crates/core/src/caps.rs` encodes per-console budgets (N64 TMEM = 4 KB); PC strict mode
validates content against them at development time.

## Testing conventions

- Every feature ships with tests in the same PR. No exceptions — the roadmap lists the
  expected tests per phase.
- Unit tests live next to the code (`#[cfg(test)]`). `core` uses
  `#![cfg_attr(not(test), no_std)]` so tests can use std.
- Golden-image tests (Fase 1+) live in `tests/golden/`; regenerate only via
  `cargo xtask test --bless` and review the diff in the PR. Performance work must leave
  goldens byte-identical.
- Guard tests: `dep_graph`, `agents_sync` (skill mirrors), `scene_codegen` (exported
  scene drift), `showcase_render` (runtime == codegen pixels), `feature_matrix`
  (`docs/TESTING.md`, the feature → test matrix). See the `test-all` skill.
- Every feature has an integration test through the public API
  (`crates/<crate>/tests/`, end to end) and a row in `docs/TESTING.md`.
- Console tests report through debug channels — ISViewer magic strings on
  N64 (`apps/n64/src/lib.rs::run_self_test`), `svcOutputDebugString` on 3DS
  (`apps/3ds/src/main.rs::run_self_test`, read from Azahar's log file).
  `cargo xtask test n64|3ds` runs them locally; CI boots both (the ares Docker
  image, and the pinned Azahar under Xvfb).
- Every engine service has a step in `castle64::selftest`, the same code on
  PC (`xtask/tests/engine_checks.rs`), in ares and in Azahar. A new
  console-visible feature adds a step there.
- Emulator golden: `tests/golden/n64/showcase.png` is compared pixel-exactly
  by `test n64`. A renderer change on the N64 path re-blesses it
  (`--bless`), and the PNG diff gets reviewed like any golden.
- 3DS goldens: `tests/golden/3ds/castle64_hub.png` (top),
  `castle64_hub_bottom.png` (the same frame's touch screen) and
  `showcase_bottom.png` (the showcase's touch panel), compared within a
  tolerance by `test 3ds` (Azahar's pixels depend on the host OpenGL);
  `n3ds_parity` holds the PC's N3ds look to castle64's two (not to the
  text-heavy showcase panel: see the pitfall on PC 3DS text).
- Performance is gated: `xtask/tests/perf_budget.rs` pins castle64's T&L
  work per scene (`tests/perf/castle64_work.toml`), and `test n64` pins
  the emulated frame cost (`tests/perf/castle64_n64.toml`). Quote the
  scene table before/after for T&L or backend changes, and bless on
  purpose. `bench_tnl` measures host CPU only.

## Toolchain notes

- Workspace builds on **stable** (see `rust-toolchain.toml`). Console target
  builds run on **nightly** with `-Zbuild-std=core,alloc`: the N64 against
  `platforms/n64/mips-nintendo64-none.json` (plus `-Zjson-target-spec`), the
  3DS against the built-in `armv6k-nintendo-3ds` — never change pins or the
  target spec casually; they are verified combinations.
- Linux: the PC crates need `pkg-config` + ALSA headers (`libasound2-dev`).
- Console code is `cfg`-gated on the host, so `cargo check` there proves nothing —
  type-check for real with nightly + `-Zbuild-std` (commands in the `test-all` skill).
- Windows: N64 builds need Docker reachable from WSL2 (Docker Desktop optional —
  a plain in-WSL dockerd works; xtask calls `wsl docker ...`). 3DS builds need
  a local devkitPro install (`3ds-dev` packages). PC development needs nothing
  beyond Rust.

## Pitfalls

- **Never compare a `Caps` with `==` to tell the console.** A tier's table differs
  (`Caps::N64_EXPANDED != Caps::N64`) and the PC renderer's carries its picture size.
  Compare `caps.base()` with the console's table, or ask the renderer's profile
  (`PcRenderer::profile()`), as `runner-pc::sprite_platform` and the editor's budget do.
- **Azahar's log and `qt-config.ini` are per user, not per worktree.** Two `test 3ds`
  runs at once (two worktrees, two sessions) read each other's log lines and flip each
  other's `is_new_3ds` / GPU-timing settings: a failure naming a step your branch does
  not have is the other run's. Run one Azahar at a time (`pgrep -f AppRun`).
- **Tier data must stay a twin, never a third copy.** A console bake writes one blob per
  asset, or a `base` and an `expanded` one (`tier_twins`); the runtime loads the index
  lines whose 4th column is empty or its tier. A new per-tier asset kind goes through
  `tier_twins` and `TierBlob::index_line`, or the expanded tier loads both copies.

- **The PC `gamepad` feature is compiled by no default gate.** fmt, clippy and
  `cargo test --workspace` build without it, so gilrs code can rot unseen. Check it with
  `cargo clippy -p trino-platform-pc --features gamepad --all-targets -- -D warnings`.
  Without `libudev-dev`, point `PKG_CONFIG_PATH` at a scratch `libudev.pc`
  (`Libs: -L<dir> -ludev`, with `<dir>/libudev.so` → the system's `libudev.so.1`).
  With a pad plugged in, `rebinding_keys_through_the_platform` fails there (it asserts
  that no pad is connected); unplug it or skip that test.
- **Keep gamepad logic out of the gilrs glue.** `PcInput::merge_pad` folds a
  device-free `PadReading`, so the mapping is tested without a pad or the feature;
  `read_gilrs` only copies values.
- **A bare `cargo run -p trino-editor` shows the project launcher.** Scripts and CI
  that want the editor pass a project (`-- .` for the engine's own content) or set a
  scene hook (`TRINO_EDITOR_SCENE`, `_TAB`, `_SELECT`, ...).
- **The editor's fonts have no `→` (or other arrow) glyph:** it draws as a box. Use
  words or a Phosphor icon (`theme::icon`).
- **`cargo test` / `cargo clippy` do not rebuild `target/debug/trino-editor`.** Before
  a screenshot with the editor hooks, run `cargo build -p trino-editor`, or the
  picture shows the old UI.
- **Templates and scaffold tests write under `target/test-projects/`, never the
  system temp dir** (a RAM disk on some machines). A scaffolded project's `cargo
  check` shares the engine's `target/` (`CARGO_TARGET_DIR`).

- **N64 FFI: no scalar float after an integer argument.** Rust is o32 and libdragon
  is o64, so the float arrives as garbage. Pass 16.16 fixed point (`u32`) or a
  pointer (ADR 0005 §6).
- **N64 z precision is 16-bit.** Coplanar surfaces need centimetres of separation at
  gameplay distances, or they z-fight on the console but not on PC (Depth32Float).
  The ares golden catches it.
- **Azahar's file log flushes only on errors.** The harness turns on
  `instant_debug_log`, so don't remove it.
- **N64 link: Rust's `compiler_builtins` defines `memcpy/memset/memmove/memcmp`
  as weak generic loops and wins over newlib** once its object is linked.
  `-Wl,-u,<sym> -Wl,-lc` ahead of the staticlib fixes it. The gcc driver
  silently drops a repeated plain `-lc`, so it must be `-Wl,-lc`. Read the map's
  memory section, not "Discarded input sections". `check_mem_symbols` guards it.
- **Code layout moves N64 timings ~20% per stage** (ares is reproducible per ROM,
  but I-cache conflicts are not). Never claim a small win from one build: A/B on
  identical code and judge on the scene table, not on a synthetic bench. When the
  `micro-*` scenes (unchanged code) move too, it is layout. Check hot function sizes
  with `mips64-elf-nm -S --size-sort`: `tessellate_with` was a 60 KB inlined body
  against a 16 KB I-cache until it was split.
- **N64 submit is store-bound.** libdragon's rspq buffer is `malloc_uncached`, and
  `rdpq_triangle` writes 26 words per triangle into it. Shaving the conversion math
  before it doesn't help (it overlaps the drain); only fewer triangles or fewer words
  do.
- **A new surface or light feature must reach the RSP path.** Most N64 draws run on
  `rsp_trino.S`, which silently ignores what it doesn't implement. Exclude the feature
  in `rsp_eligible`, or implement it in the overlay behind the oracle and parity
  checks (`engine-feature` › 1).
- **RSP fixed point:**
  - the overlay's `vrcph/vrcpl` of an s15.16 w is 1/(2w);
  - z must come from 1/depth with the CPU path's rounding, or touching surfaces flip
    between RSP and CPU draws;
  - reuse a single triangle staging buffer.
- **Translucency turns depth splits on.** `split_policy` bisects only fogged,
  textured or translucent draws (tint or vertex alpha < 255). A tint with alpha < 255
  on a big mesh brings back DEPTH_SPLIT's extra triangles on the N64.
- **3DS: never draw 3D with `C2D_DrawTriangle`.** It takes one depth per triangle,
  so big floors cover what stands on them. Everything goes through
  `trino_3d_draw` (per-vertex depth).
- **A big game struct used to be built on the N64 stack before boxing.** `boxed`
  (host.rs) now writes it into `Box::new_uninit()`, which lets the compiler build it in
  place. An external project's stack peak fell from 60.5 to 33.5 KB. Keep that pattern
  for any large heap object.
- **The N64 main stack is 64 KB and an overflow is silent** (memory corruption, random
  hangs; interrupts push onto it too). A ~22 KB struct built by value (`ShowcaseGame`)
  overflowed it in the self-test. `Box::new(big())` still builds the temporary in the
  caller's frame, so put such steps in their own `#[inline(never)]` function.
  `check_stack` fails the self-test above 60 KB.
- **Renderer state (camera, light) outlives frames and games.** A game that never
  calls `set_light` inherits the last one. On consoles the self-test's showcase
  fog leaked into castle64. Set both every frame.
- **`Caps::N64.max_tris_per_frame` is not the CPU T&L budget.** A 30 fps frame
  affords roughly 550–650 source triangles today, fewer with many draws. Use
  `model inspect`'s N64 cost estimate. Strict mode enforces
  `Caps::max_3d_us_per_frame` (N64: 50 ms estimated, CPU and RSP each).
- **glTF COLOR_0 is linear.** The bake converts it to display sRGB, so write linear
  values (the generators use `color0_linear`). Before 2026-10-13, Blender-painted
  colors baked much darker.
- **Hidden faces still cost N64 CPU.** A face buried inside another part, or a back
  face, pays its transform. Build models from visible faces only (`blender-asset`).
  Don't union parts with a boolean: it cuts holes and adds triangles.
- **In WGSL, never `let`-copy a uniform struct that holds an array you index
  dynamically.** `let set = sets.sets[i]` puts the whole struct in private memory and
  every `set.lights[j]` reads it back from scratch, per pixel. The PC lit pipeline did
  that: an external project's 4K frame took 19.1 ms instead of 8.6 ms on a Renoir iGPU.
  Take a pointer (`let set = &sets.sets[i];`, then `(*set).lights[j]`).
- **In WGSL, never index a local array with a runtime value either.** The SSAO's 4×4
  Bayer table (`var m = array<u32, 16>(..); m[i]`) lived in scratch memory per pixel and
  nearly doubled the pass on a Renoir iGPU (1080p 11 → 6.7 ms once it became bit
  arithmetic). Compute such patterns, or put the table in a uniform.
- **Two example game crates can't link into one test binary.** Each runs
  `export_game!`, so `hello-sprite` with `platformer` (or `castle64`) fails with
  duplicate `trino_game_*` symbols. Give each its own test file and share helpers
  through a `tests/<dir>/mod.rs` (`xtask/tests/ao_evidence/`).
- **A manifest option that changes no baked byte reaches no one.** The asset watcher
  reports changed bytes only. `ao` on a convex model (no self-occlusion, no `ground`)
  bakes the same TMDL, so the editor's model state would never refresh. The editor
  updates its copy when it writes the manifest. Any new manifest-only option needs the
  same.
- **Template manifests are `Cargo.toml.tmpl`.** A placeholder `Cargo.toml` anywhere in
  the repo breaks every git-dependency user, because cargo scans the whole repository.

- **I4/I8 textures take alpha from RGB.** A font atlas with white transparent
  texels drew every glyph as a solid block on the N64 only. The bake now writes
  transparent texels black. Any white-mask sprite in I4/I8 needs the same.

  `cargo xtask scene export scenes/showcase.scene.ron examples/showcase/src/showcase_gen.rs`
  (`scene_codegen` fails otherwise). Then decide the field in `MemoKey::new` and
  `rsp_eligible`.
- **glTF custom attributes lose their underscore in the `gltf` crate:** `_SLOT` is
  `Semantic::Extras("SLOT")`. Blender exports them only with `export_attributes=True`
  (`export_glb` sets it), and always as float SCALAR, even from INT attributes.
- TMDL is extensible by **sections** (`BNDS`, `SKEL`, `ANIM`; unknown tags are skipped):
  add data as a new section instead of changing the base layout.
- Rigid skeletons: ≤ 32 joints (`MAX_JOINTS`, stack-allocated), parents before children,
  one skin per file, heaviest weight wins.
